# invoice-pdf-hub

[한국어](./README.md) | [日本語](./README.ja.md)

> 회사에서 다루는 PDF 문서를 다운로드 없이 브라우저에서 미리보기·편집·저장할 수 있는 웹 서비스
> (자연어 명령으로 문서를 수정하는 AI 에이전트 기능까지 확장 예정)

## 배경

MIC 회사의 인턴으로 경험했을 때, 상품 배송 관련 업무 중, 송장 PDF 파일을 다루는 과정이 불편하다는 이야기를 들었다.

1. 송장 PDF를 시스템에 업로드
2. 수정이 필요하면 PDF파일을 다운로드
3. 수정
4. 수정본 PDF를 다시 업로드
5. 다음 근무자가 PDF를 확인/수정하려면 위의 과정을 반복

이 불편함은 송장뿐 아니라 계약서, 견적서, 각종 사내 문서 등 **회사에서 다루는 PDF 문서 전반**에 공통적으로 해당하는 문제입니다. 그래서 이 프로젝트는 특정 문서 종류에 한정하지 않고, **어떤 PDF 파일이든 다운로드-수정-재업로드 과정 없이 웹에서 바로 처리**할 수 있는 서비스를 목표로 합니다.

## 프로젝트 범위

- **Phase 1**: 범용 PDF 업로드·미리보기·버전관리·수동 편집 (지금 진행 중)
- **Phase 2**: 자연어 명령으로 문서를 수정하는 AI 에이전트 (예: "배송지를 서울로 바꿔줘", "날짜를 8월 20일로 변경해줘")

## 주요 기능 (Phase 1)

- [ ] **최근 파일 미리보기 (최대 10개)** — 최근 업로드/수정된 PDF 목록을 썸네일과 함께 표시
- [ ] **다운로드 없는 미리보기** — 현재 업로드된 파일을 다운로드하지 않고 브라우저에서 바로 확인
- [ ] **웹 내 편집 및 저장** — 미리보기 화면에서 사용자가 수정할 필드를 직접 클릭해 지정하고 값을 바꾸면, 수정된 파일이 최종본으로 저장됨 (문서 양식이 제각각이어도 동작하도록 좌표를 하드코딩하지 않고 사용자가 그때그때 지정하는 방식)

## 주요 기능 (Phase 2 — AI 에이전트)

Phase 1에서 만든 편집 로직은 그대로 두고, 그 앞단에 **자연어 명령을 해석하는 레이어**만 추가하는 구조입니다.

```
사용자: "배송지를 서울로 바꿔줘"
        │
        ▼
AI가 해석 (LLM function calling)
   { action: "replace_field", field: "배송지", new_value: "서울" }
        │
        ▼
Phase 1의 편집 로직 그대로 실행 (PyMuPDF redaction)
```

- [ ] 자연어 명령 → 구조화된 수정 지시 변환 (Claude/OpenAI function calling 활용)
- [ ] 해석된 지시를 Phase 1 편집 엔진에 연결
- [ ] 애매하거나 위험한 명령(예: 금액 관련 수정)은 실행 전 사용자 확인 단계 추가

## 기술 스택

| 영역 | 기술 |
|---|---|
| 언어 | Python |
| 웹 프레임워크 | Django |
| PDF 처리 | PyMuPDF (fitz) — 렌더링, 텍스트 추출, 편집(redaction) |
| DB | SQLite (개발용) → PostgreSQL (운영 전환 고려) |
| 파일 저장 | 로컬 디스크 (개발용) → AWS S3 / MinIO (운영 전환 고려) |
| 프론트엔드 | Django Template + Bootstrap (브라우저 내장 PDF 뷰어 활용) |
| AI (Phase 2) | LLM API (Claude / OpenAI) — function calling으로 자연어 명령을 구조화된 데이터로 변환 |

## 아키텍처

```
브라우저 (Django Template)
     │  업로드 / 조회 / 수정 요청 (직접 클릭 또는 자연어 명령)
     ▼
API 서버 (Django)
     │
     ├──▶ 메타데이터 DB (파일 정보, 버전 이력)
     ├──▶ 파일 저장소 (PDF 원본 및 버전별 파일)
     └──▶ (Phase 2) AI 해석 레이어 — 자연어 명령을 구조화된 수정 지시로 변환 후 편집 엔진 호출
```

- 파일 자체는 DB가 아닌 별도 저장소에 저장하고, DB에는 메타데이터(파일명, 버전, 업로더, 수정시각, 경로)만 저장
- 수정할 때마다 기존 파일을 덮어쓰지 않고 새 버전으로 저장 → 누가 언제 수정했는지 이력 추적 가능
- AI 해석 레이어는 편집 로직을 직접 건드리지 않고, Phase 1에서 만든 편집 엔진을 그대로 호출만 함 → 두 단계가 분리되어 있어 Phase 2를 나중에 붙여도 기존 구조를 갈아엎을 필요 없음

## 개발 로드맵

**Phase 1**
1. **MVP**: 파일 업로드 + 최근 10개 목록 + 브라우저 내 미리보기
2. 버전 이력 기능 추가 (누가 언제 수정했는지 기록)
3. 사용자가 PDF 화면에서 직접 필드를 클릭해 지정하는 편집 기능 (PyMuPDF redaction으로 값 교체 후 새 버전 저장)

**Phase 2**
4. LLM function calling으로 자연어 명령 → 구조화된 수정 지시 변환
5. 변환된 지시를 Phase 1 편집 엔진에 연결
6. 위험한 수정(금액 등)에 대한 확인 단계 추가

## 편집 기능 구현 방향

PDF는 Word 문서처럼 구조화된 텍스트가 아니고, 문서 종류가 다양해질수록 필드 위치를 미리 코드에 고정해두는 방식은 한계가 있습니다. 그래서 **사용자가 미리보기 화면에서 수정할 위치를 직접 클릭해 지정**하고, 그 좌표를 기준으로 PyMuPDF의 redaction 기능으로 값을 교체하는 방식을 사용합니다.

```python
doc = fitz.open(file_path)
page = doc[0]
rect = page.search_for("기존 텍스트")[0]   # 또는 사용자가 클릭한 좌표
page.add_redact_annot(rect)
page.apply_redactions()
page.insert_text(rect.tl, "새 텍스트", fontsize=10)
doc.save(new_version_path)
```

Phase 2에서는 이 좌표 지정 과정을 AI가 문서 내용을 이해해서 대신 찾아주는 방향으로 발전시킬 계획입니다.
